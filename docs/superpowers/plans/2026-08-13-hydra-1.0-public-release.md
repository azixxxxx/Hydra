# Hydra 1.0 Public Release Plan

> **Execution note:** Implement this plan test-first. Use `superpowers:test-driven-development` for each behavior change and `superpowers:verification-before-completion` before any release claim. Do not commit, tag, push, or publish without the user's explicit Git/release approval.

**Status:** Automated implementation and local installation gates completed on 2026-08-13. The maintainer has now attested that usage credits are disabled and authorized the bounded live release matrix, initial commit, push, tag, and GitHub publication. Final evidence is recorded in `docs/verification/2026-08-13-hydra-1.0.md`.

**Date:** 2026-08-13

**Goal:** Turn the current local Hydra implementation into a credible public `1.0.0` Codex plugin with a small stable contract, honest platform support, durable state behavior, and a reproducible GitHub installation path.

**Historical verdict at plan creation:** **NO-GO**. The blockers described below drove the implementation. The current evidence and remaining publication boundary are recorded in `docs/verification/2026-08-13-hydra-1.0.md`.

**Architecture:** Keep the existing local TypeScript STDIO MCP server, detached workers, explicit Claude CLI subprocesses, durable filesystem state, process-group cancellation, controlled settings, and isolated Git worktrees. Reduce the public surface before freezing it. Do not add a service, UI, cloud dependency, automatic model fallback, or learned routing for 1.0.

## Priority definitions

- **P0:** Correctness, security, persistence, or contract blocker. Every P0 must be closed before `1.0.0-rc.1`.
- **P1:** Public operability and maintainability requirement. Every P1 must be closed before stable `1.0.0`; an RC may expose unfinished P1 work explicitly.
- **P2:** Deliberately outside 1.0. P2 work must not delay the stable tag.
- No P0 or P1 may be silently waived. A changed decision must be recorded in this document with evidence and user approval.

## Verified starting point

The existing verification report records successful macOS arm64 live probes for Sonnet, Opus, Fable, continuation, cancellation, and isolation, and exact requested model families. A fresh `npm run check` during planning exited 0 with 266 passing tests, five skipped real-only tests, lint, strict typecheck, build, and plugin validation. That evidence remains valuable but is not sufficient for 1.0 because the new architecture panel reproduced two paths not covered by the suite.

### Newly reproduced P0 defects

1. **Per-run continuation turn accounting is incorrect.** The event accumulator overwrites its invocation count with the terminal `num_turns` value. A resumed Claude session may report a cumulative session count, and the adapter applies the per-run cap to that value, producing a false `CLAUDE_TURN_LIMIT` after a successful continuation.
2. **The persistence guard can reject already-sanitized benign output.** The sanitizer emits a canonical redaction marker, but the storage backstop still matches an authorization-shaped phrase containing that marker. A complete Opus architecture result was rejected at final persistence and survived only in the exact Claude session transcript.

Both defects block `1.0.0-rc.1`. Avoiding the triggering vocabulary or retrying with a new session is not an acceptable workaround.

### Newly confirmed routing P0

3. **Fan-out is bounded by process count but not by replicated context or aggregate usage.** `RouteInput` accepts `parallelizable`, but the current policy does not use it. Several routes can recommend two or three broad repository sessions without measuring shared-context overlap, requiring distinct scopes, or exposing the lower-bound context duplicated into every session. A nominally lower-tier model multiplied by several fresh contexts may consume more input and cache-creation tokens than one stronger model that resolves the task once.

This blocks the 1.0 route-contract freeze. Hydra must not equate “up to three sessions” with an economically bounded delegation. Exact pre-call token use remains unknowable, so the contract must expose honest byte-based lower bounds and post-run reported usage rather than a synthetic cost or quota estimate.

### Confirmed public-release gaps

- No root license, public README, changelog, security policy, contribution policy, repository metadata, CI, or release workflow.
- Placeholder author and `UNLICENSED` plugin metadata.
- Version identity differs between `package.json`, the plugin manifest, and the MCP server literal.
- The declared Node 20 floor is end-of-life and differs from the verified runtime.
- README claims Linux support that the maintainer cannot verify.
- The build output required by `.mcp.json` is ignored by Git.
- Configuration is unversioned, persists resolved defaults, and can make server startup fail.
- State records use exact schema literals while scans can omit invalid records without exposing degraded health.
- All current eight tools lack public output schemas; status has polymorphic single/list shapes and generic array wrapping.
- Optional-input tools can reject a completely omitted arguments object at the MCP transport boundary.
- Billing and context selectors were removed during the contract-freeze work; subscription authentication and controlled context are unconditional.
- Unknown Claude CLI versions are not classified separately from a verified compatibility profile.
- Continuations use current global turn/time defaults instead of a durable session policy snapshot.
- Routing caps only the number of sessions. It ignores `parallelizable`, shared-context size, scope overlap, staged activation, and aggregate reported usage.
- Early detached-worker failures, retention failures, and process-marker variance need public-grade diagnostics and regression coverage.

## Target public contract

### Stable tools

The 1.x tool names are:

1. `hydra_preflight`
2. `hydra_route`
3. `hydra_start`
4. `hydra_status`
5. `hydra_result`
6. `hydra_continue`
7. `hydra_cancel`
8. `hydra_record_outcome`
9. `hydra_budget`

`hydra_budget` records or reads a manual plan-usage snapshot and computes a dry-run pacing decision. It never invokes Claude, retrieves account data, opens a browser, or enables usage credits. Diagnostic health remains in preflight/status rather than becoming another tool.

### Response envelope

Every tool must declare an MCP `outputSchema` and return one documented structured shape:

```ts
type HydraSuccess<T> = {
  schemaVersion: 1;
  hydraVersion: string;
  response: {
    ok: true;
    data: T;
    warnings: SafeWarning[];
  };
};

type HydraFailure = {
  schemaVersion: 1;
  hydraVersion: string;
  response: {
    ok: false;
    error: {
      code: HydraErrorCode;
      message: string;
      details?: Record<string, JsonValue>;
    };
  };
};
```

Rules:

- `response.ok` is a required JSON-Schema discriminator. Success requires `response.data` and `response.warnings`; failure requires `response.error`.
- `hydra_status` always returns `{ jobs: JobSummary[], health: HealthSummary }` inside `response.data`. Supplying `jobId` filters the list to zero or one item; it does not change the envelope.
- `hydra_result` remains bounded and paginated. Event offsets, limits, truncation flags, and next cursors are explicit.
- Tools with entirely optional inputs accept both an omitted arguments object and `{}`.
- Errors use stable documented codes. A 1.x release may add a code but may not repurpose an existing code.
- A 1.x release may add optional output fields and widen accepted inputs. It may not remove fields, change their meaning, or make an optional input required.
- Internal raw Claude events and private filesystem layout are not public compatibility contracts unless explicitly documented.

### Delegation economics contract

`hydra_route` must return a staged delegation plan, not an unordered list that implies every recommended session should start immediately:

```ts
type DelegationStrategy =
  | 'none'
  | 'single'
  | 'sequential-escalation'
  | 'partitioned-parallel'
  | 'independent-panel';

type SessionActivation =
  | 'immediate'
  | 'if-unresolved'
  | 'if-contradiction'
  | 'manual';

type DelegationPlan = {
  strategy: DelegationStrategy;
  maxImmediateSessions: number;
  maxTotalSessions: number;
  sharedContextBytes: number;
  replicatedContextBytesImmediate: number;
  replicatedContextBytesAllActivated: number;
  contextEstimateCaveat: string;
  sessions: Array<SessionRecommendation & {
    activation: SessionActivation;
    distinctQuestion: string;
    scope: string[];
    contextPolicy: 'capsule' | 'delta';
  }>;
};
```

Routing rules:

- Default to one immediate external session. “Maximum” means maximum justified reasoning quality within hard limits, not maximum agent count.
- For broad, high-overlap context, prefer one stronger lead model over several nominally cheaper fresh sessions.
- Start another session only for a distinct unresolved question, a falsifiable adversarial check, or a genuinely disjoint scope.
- `parallelizable: false` forbids parallel starts. `parallelizable: true` permits them only when the route also proves low overlap and names non-overlapping scopes.
- Ordinary review uses one Sonnet or one Opus. It does not fan out generic “review the repository” prompts.
- An explicit independent panel may start two members with the same bounded capsule because independence is the product requirement. A third member is conditional and must add a named missing perspective.
- Reuse a saved session when the same context and role are materially useful. Do not create a fresh agent merely to continue the same line of reasoning.
- Every additional activation records why the lead result was insufficient. If no distinct marginal question exists, stop.

Context rules:

- Build one context capsule containing the objective, constraints, Git identity, precise file/evidence references, and open questions. Do not replay the full host conversation or another agent's transcript.
- Default capsule limit is 32,768 UTF-8 bytes. A larger capsule requires an explicit warning and remains subject to the existing task-size hard limit.
- Other agents receive the capsule plus only their narrow role-specific delta. They may inspect cited repository evidence but should not repeat broad discovery without a documented gap.
- `replicatedContextBytesImmediate` and `replicatedContextBytesAllActivated` are exact byte multiplication for the supplied capsule only. Durable summaries add actual activated replication. These values are explicitly not token, dollar, Max-allowance, system-prompt, cache, or repository-read estimates.

Observation rules:

- Link jobs created by one delegation under a durable group identifier rooted at the first job.
- Persist each job's reported input, output, cache-read, and cache-creation tokens and aggregate them per delegation without converting them into remaining allowance.
- Record accepted/rejected outcome and actual usage together so a user can see whether the second or third session added evidence worth its context tax.
- 1.0 uses these metrics for visibility and deterministic stop rules only. Automatic learned routing remains Phase 4.

### Weekly allowance and token-efficiency contract

Anthropic currently documents fixed weekly reset times visible in Settings → Usage and multiple weekly buckets, while its public pages use changing bucket labels. Usage is also affected by conversation length, tools, model, effort, and activity on other Claude surfaces. Hydra therefore treats bucket names and applicability as user-supplied opaque data rather than hardcoding “Sonnet”, “Opus”, or “all-model” assumptions. See [Max plan limits](https://support.claude.com/en/articles/11049741-what-is-the-max-plan), [usage-limit best practices](https://support.claude.com/en/articles/9797557-usage-limit-best-practices), and [usage and length limits](https://support.claude.com/en/articles/11647753-how-do-usage-and-length-limits-work).

The official pre-call token-counting endpoint requires an API credential. Hydra remains subscription-only and must not call it. It records exact UTF-8 bytes supplied by Hydra, uses conservative local forecasts keyed by exact Claude model/version, and treats Claude CLI token fields as post-run observations. It never claims that local tokens equal weekly allowance percentage. The official endpoint itself describes its result as an estimate and warns that newer model families can use a different tokenizer; see [Claude token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting).

#### Manual snapshot schema

```ts
type UsageBucketSnapshot = {
  bucketId: string;
  displayLabel: string;
  window: 'five-hour' | 'weekly';
  appliesTo: Array<'sonnet' | 'opus' | 'fable' | 'all'>;
  capturedAt: string;
  cycleStartedAt: string;
  resetAt: string;
  remainingBasisPoints: number; // integer 0..10_000 from Settings → Usage
};

type UsageBudgetSnapshot = {
  schemaVersion: 1;
  source: 'manual-settings';
  buckets: UsageBucketSnapshot[];
  usageCreditsDisabledAttestedAt: string;
  exclusiveHydraActivitySincePreviousSnapshot: boolean;
};
```

Rules:

- Persist percentages as integer basis points and reset times as absolute instants. Never infer a weekly reset weekday from local time.
- Store neither account identity nor screenshots. A newer snapshot supersedes the previous active snapshot but history remains append-only for calibration and audit.
- Snapshot freshness is part of the decision. Defaults: at most 12 hours old in normal pacing and at most 60 minutes old during final burn. Stale or internally inconsistent data yields `BUDGET_SNAPSHOT_STALE` and disables aggressive routing.
- Every applicable bucket is a hard constraint. A model job must fit the weekly bucket or buckets and the current five-hour window. The tightest bucket wins.
- A changed model version, tokenizer family, Claude CLI compatibility profile, or effort class starts a new calibration cohort.
- Usage on claude.ai, Claude Desktop, Cowork, or direct Claude Code shares allowance and can invalidate Hydra-only inference. Non-exclusive intervals are retained as contaminated observations but do not tighten the central estimator.

#### Token forecast

For job candidate `j`, persist the feature vector without collapsing it into fake currency:

```text
x_j = (promptBytes, roleBytes, schemaBytes, referencedBytes,
       expectedTurns, toolClass, modelId, claudeVersion, effort)
y_j = (inputTokens, outputTokens, cacheReadTokens, cacheCreationTokens)
```

- Before sufficient history exists, route one job at a time and require a fresh snapshot after each calibration batch.
- With sufficient clean observations, compute a non-negative model/version-specific upper prediction `q95(b, j)` for each applicable quota bucket. Use a documented rolling conformal or empirical 95th-percentile bound; do not use an unqualified mean.
- Snapshot-to-snapshot allowance deltas calibrate quota fractions. Reported token vectors explain the local jobs inside that interval but never become a universal Anthropic billing formula.
- If a statistically supported upper bound is unavailable, the budget state is `uncalibrated`. Hydra may run the task at its quality floor but may not claim that it will fit a weekly surplus or activate a fan-out burn.
- Cache-read and cache-creation values remain separate because their effect on plan usage is not documented as interchangeable.

#### Deterministic weekly pacing curve

For every weekly bucket `b`, let `τ` be hours until its reset, `W` its observed cycle length, `H = 24h` the burn window, `B = 2h` the finish buffer, `r24 = 0.20` the target remaining fraction at burn start, `rmin = 0.03` the hard reserve, and `γ = 1.5` the burn exponent. These defaults are bounded configuration, not hidden constants.

```text
if H < τ <= W:
  targetRemaining(τ) = r24 + (1 - r24) * (τ - H) / (W - H)

if B < τ <= H:
  z = (τ - B) / (H - B)
  targetRemaining(τ) = rmin + (r24 - rmin) * z^γ

if 0 <= τ <= B:
  targetRemaining(τ) = rmin
```

This spends approximately 80% by the start of the final day, then deliberately converges toward a 3% reserve two hours before reset. At each decision point:

```text
lowerBoundRemaining_b = snapshotRemaining_b
                        - calibratedHydraConsumptionUpperBound_b
                        - roundingAndStalenessMargin_b

surplus_b = lowerBoundRemaining_b - targetRemaining_b
```

The controller uses the minimum feasible surplus across all buckets applicable to the candidate model. Negative surplus selects conservation; positive surplus permits catch-up; final burn requires `τ <= 24h`, a fresh snapshot, a positive lower-bound surplus, and a recent manual attestation that usage credits are disabled.

#### Quality invariant

Budget optimization is lexicographic:

1. satisfy the task's model/effort/evidence quality floor;
2. preserve subscription-only and isolation guarantees;
3. minimize duplicated context and the conservative usage bound;
4. use confirmed expiring surplus on additional valuable backlog evidence.

The controller may compact context, reuse a session, defer non-urgent work, suppress redundant fan-out, or stop. It may not downgrade a critical architecture/review task below its quality floor, shorten mandatory verification, switch models silently, enable paid credits, or manufacture work merely to consume allowance. During final burn, extra capacity is used in this order: user-supplied blocked backlog, stronger verification/tests, one distinct adversarial review, then an explicitly justified panel. If no valuable work exists, allowance expires unused.

`hydra_budget` reports one of `unknown`, `uncalibrated`, `conserve`, `on-track`, `catch-up`, `final-burn`, or `paused`, together with snapshot age, per-bucket target/remaining/surplus, uncertainty, and the exact reason. `hydra_route` consumes that decision but still returns a dry-run staged plan; only an explicit `hydra_start` or `hydra_continue` spends allowance.

### Version identity

- `package.json` is the single authored version source.
- The build injects the exact version into the plugin manifest, MCP server metadata, bundles, preflight/status envelopes, and release artifact metadata.
- Local development cache-buster metadata may be appended only by an installation step; the base SemVer must still equal the package version.
- CI fails if any generated version differs.

### Task 3.4: Preserve quality while changing spend rate

- [ ] Encode reviewed quality floors by task kind/risk before budget selection. Budget state cannot lower the required model, effort, evidence schema, isolation, or verification.
- [ ] In conservation mode, first remove duplicated context and speculative fan-out; then defer non-urgent work. Never silently substitute a lower model for a required Opus/Fable decision.
- [ ] In final burn, rank only a user-supplied backlog by value, urgency, uncertainty reduction, and readiness. Consume surplus by completing useful work, strengthening tests/review, or activating an already justified conditional session.
- [ ] Require a distinct expected information gain for each added session. A larger remaining percentage alone never authorizes a generic fan-out.
- [ ] Return `no-valuable-work` when the backlog is empty or blocked. Expiring unused allowance is safer than fabricated work.

### Task 3.5: Deterministic proof suite

- [ ] Use a fake clock to test cycle start, exactly 24 hours, exactly two hours, reset, timezone/DST-independent instants, and multiple buckets with different reset times.
- [ ] Test basis-point rounding, stale snapshots, missing attestation, uncalibrated cohorts, contaminated intervals, unknown model versions, external use, in-flight reservations, cancellation, timeout, crash, and restart.
- [ ] Prove that a high-value task keeps its quality floor in every mode, while redundant fan-out is suppressed under both scarcity and surplus.
- [ ] Prove the target curve reaches 20% at burn start and 3% at the finish buffer with monotonic, bounded fixed-point results.
- [ ] Prove no test or CI path invokes Claude, token-counting APIs, browsers, private endpoints, or usage credits.
- [ ] Add a dry-run week simulation with randomized workloads and invariants: no bucket oversubscription under the conservative model, no paid overflow path, no quality-floor downgrade, and no synthetic quota claim.

**Exit criteria:** A fresh manual snapshot produces a reproducible per-bucket decision; stale/uncalibrated data disables aggressive mode; the final-day curve spends only conservative verified surplus; all admission reservations recover across restart; and quality floors remain invariant.

Consensus adopted:

- Linux is not a 1.0 gate and must be described as experimental/community-owned.
- The public Node floor remains `>=20.9.0`; release evidence must name the exact macOS runtime actually exercised.
- The two live panel failures block the RC.

Resolved disagreements:

- **State:** implement a 1.0 compatibility mechanism without 0.1 transforms, but rehearse it against a copied real pre-1.0 state and preserve all evidence.
- **Distribution:** commit reproducible `dist` because the supported channel is a clone-based local marketplace and users should not need a compiler for first launch.
- **Unknown Claude versions:** warn based on version, block based on failed behavioral safety capabilities.
- **Typed invalid/future state:** complete before stable 1.0 rather than deferring silent-omission behavior to 1.0.x.
- **Fan-out economics:** count replicated context and marginal evidence, not agents. Use one strong lead by default, conditional escalation, and an explicit bounded-panel exception.
- **Weekly pacing:** use manual opaque quota buckets and a deterministic conservative curve. Preserve quality as a hard constraint; spend confirmed surplus during the final 24 hours only on valuable user work.
